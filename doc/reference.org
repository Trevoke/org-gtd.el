** Configuration Variables Reference
:PROPERTIES:
:DESCRIPTION: All customization variables explained
:CUSTOM_ID: config-vars-reference
:END:

These variables control how org-gtd behaves. All can be customized via ~M-x customize-group RET org-gtd~.

*** Required Configuration

**** ~org-todo-keywords~ (org-mode variable)

*Type*: List of keyword sequences

*Default*: Varies by org-mode installation

*Description*: Defines TODO keyword sequences for org-mode. All GTD keywords must be in the *same sequence*.

*Required format*:
#+begin_src emacs-lisp
(setq org-todo-keywords
      '((sequence "TODO" "NEXT" "WAIT" "|" "DONE" "CNCL")))
#+end_src

The ~|~ separator marks done states (right side) from active states (left side).

*Org-mode keyword options are supported*: You can use org-mode's standard keyword syntax with fast access keys and logging options (e.g., ~"TODO(t)"~, ~"DONE(d!)"~, ~"WAIT(w@/!)"~). Org-gtd only looks at the base keyword string, so these are equivalent:

#+begin_src emacs-lisp
;; Basic
'((sequence "TODO" "NEXT" "WAIT" "|" "DONE" "CNCL"))

;; With fast access keys and logging
'((sequence "TODO(t)" "NEXT(n)" "WAIT(w@/!)" "|" "DONE(d!)" "CNCL(c)"))
#+end_src

**** ~org-gtd-keyword-mapping~

*Type*: Alist mapping GTD states to keyword strings

*Default*:
#+begin_src emacs-lisp
'((todo . "TODO")
  (next . "NEXT")
  (wait . "WAIT")
  (canceled . "CNCL"))
#+end_src

*Description*: Maps GTD semantic states to your chosen TODO keywords.

*Required keys*:
- ~todo~ :: Tasks not ready to be acted upon
- ~next~ :: Tasks ready to act on immediately
- ~wait~ :: Tasks blocked or delegated to someone else
- ~done~ :: Tasks successfully completed
- ~canceled~ :: Tasks that won't be completed

*Example*: Using custom keywords:
#+begin_src emacs-lisp
(setq org-todo-keywords
      '((sequence "TASK" "DOING" "BLOCKED" "|" "COMPLETE" "CANCELLED")))

(setq org-gtd-keyword-mapping
      '((todo . "TASK")
        (next . "DOING")
        (wait . "BLOCKED")
        (done . "COMPLETE")
        (canceled . "CANCELLED")))
#+end_src

*** Directory and File Configuration

**** ~org-gtd-directory~

*Type*: String (directory path)

*Default*: ~"~/gtd/"~

*Description*: Directory where org-gtd keeps all its files.

org-gtd creates these files in this directory:
- ~inbox.org~ - Capture target (created on first capture)
- ~org-gtd-tasks.org~ - Main GTD file containing all organized items

All GTD categories (Actions, Projects, Calendar, Tickler, Delegated, etc.) are stored as top-level headings within ~org-gtd-tasks.org~, not as separate files. These headings are created automatically when you first refile an item to that category.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-directory "~/my-gtd/")
#+end_src

*Note*: Make sure to add this directory to ~org-agenda-files~ after org-gtd loads:
#+begin_src emacs-lisp
(with-eval-after-load 'org-gtd
  (setq org-agenda-files (list org-gtd-directory)))
#+end_src

For ~use-package~, put this in the ~:config~ section.

**** ~org-gtd-additional-inbox-files~

*Type*: List of file paths

*Default*: ~nil~

*Description*: Additional inbox files to process after the main inbox.

When you call ~org-gtd-process-inbox~, it first processes all items in the main inbox (~inbox.org~). After the main inbox is empty, it continues processing items from these additional files in order.

This is useful when you capture items from multiple sources:
- Mobile apps that sync to a separate file
- Email-to-org workflows
- Context-specific inboxes (work, personal)

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-additional-inbox-files
      '("~/gtd/mobile-inbox.org"
        "~/gtd/email-inbox.org"))
#+end_src

*Note*: Each file should contain org headings at the top level, just like the main inbox.

**** ~org-gtd-horizons-file~

*Type*: String (filename)

*Default*: ~"horizons.org"~

*Description*: Name of file (in ~org-gtd-directory~) containing your GTD horizons (long-term goals, areas of focus, purpose).

This file can be displayed during clarification for context.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-horizons-file "my-horizons.org")
#+end_src

*** Capture Configuration

**** ~org-gtd-capture-templates~

*Type*: List of org-capture template specifications

*Default*:
#+begin_src emacs-lisp
'(("i" "Inbox"
   entry  (file ,#'org-gtd-inbox-path)
   "* %?\n%U\n\n  %i"
   :kill-buffer t)
  ("l" "Inbox with link"
   entry  (file ,#'org-gtd-inbox-path)
   "* %?\n%U\n\n  %i\n  %a"
   :kill-buffer t))
#+end_src

*Description*: Capture templates specific to org-gtd inbox.

*Constraints* (must be satisfied for org-gtd to work correctly):
1. Template string must start with ~"* "~ (asterisk + space for org heading)
2. Entry type must be: ~entry (file ,#'org-gtd-inbox-path)~

*Example*: Adding a custom template:
#+begin_src emacs-lisp
(setq org-gtd-capture-templates
      '(("i" "Inbox"
         entry (file ,#'org-gtd-inbox-path)
         "* %?\n%U\n\n  %i"
         :kill-buffer t)
        ("m" "Meeting note"
         entry (file ,#'org-gtd-inbox-path)
         "* Meeting: %?\n%U\n\nAttendees:\n\nNotes:\n"
         :kill-buffer t)))
#+end_src

*** Organize and Process Configuration

**** ~org-gtd-organize-hooks~

*Type*: List of functions

*Default*: ~'(org-set-tags-command)~

*Description*: Functions run when organizing each item. Each function can add metadata (tags, properties, etc.) to the item being organized.

The default value prompts for tags. Built-in options:
- ~org-set-tags-command~ :: Prompt for tags (default)
- ~org-gtd-set-area-of-focus~ :: Prompt for area of focus
- Custom functions :: Functions you write yourself

*Example*: Add effort estimation and area of focus:
#+begin_src emacs-lisp
(defun my-add-effort ()
  "Prompt for effort when organizing."
  (when (org-gtd-organize-type-member-p '(single-action project-heading))
    (org-set-effort)))

(setq org-gtd-organize-hooks
      '(org-set-tags-command
        org-gtd-set-area-of-focus
        my-add-effort))
#+end_src

*Helper function*: ~org-gtd-organize-type-member-p~
- Takes a list of item types to check against
- Returns t if current item matches one of the types
- Available types: ~single-action~, ~project-heading~, ~project-task~, ~calendar~, ~delegated~, ~tickler~, ~someday~, ~habit~, ~knowledge~, ~quick-action~, ~trash~, ~everything~

**** ~org-gtd-save-after-organize~

*Type*: Boolean

*Default*: ~nil~

*Description*: If non-nil, save all modified buffers after each organize step.

Useful if you want automatic saves during inbox processing.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-save-after-organize t)
#+end_src

**** ~org-gtd-refile-to-any-target~ (deprecated)

*Type*: Boolean

*Default*: ~t~

*Deprecated*: As of 4.0.0. Use ~org-gtd-refile-prompt-for-types~ instead.

*Description*: Control refile behavior when organizing items. This variable is deprecated and will show a warning when used.

- When ~t~: org-gtd will refile to the first target it finds without prompting (deprecated behavior)
- When ~nil~: org-gtd consults ~org-gtd-refile-prompt-for-types~ to decide per item type

*Migration*: To migrate to the new system:

#+begin_src emacs-lisp
;; Step 1: Set the deprecated variable to nil (required)
;; This enables per-type control via org-gtd-refile-prompt-for-types
(setq org-gtd-refile-to-any-target nil)

;; Step 2 (optional): Customize which types prompt
;; The default prompts for most types except quick-action, knowledge, trash
;; Only change this if you want different behavior:
;; (setq org-gtd-refile-prompt-for-types '(project-heading project-task))
#+end_src

See [[#controlling-refile-prompts][Controlling Refile Prompts by Item Type]] for the new approach.

**** ~org-gtd-refile-prompt-for-types~

*Type*: List of symbols

*Default*: ~(single-action project-heading project-task calendar someday delegated tickler habit)~

*Description*: List of GTD item types that should prompt for refile target selection when organizing.

- Types in the list prompt user to choose from available refile targets
- Types *not* in the list auto-refile to the first available target
- Only consulted when ~org-gtd-refile-to-any-target~ is ~nil~

*Valid type symbols:* ~single-action~, ~project-heading~, ~project-task~, ~calendar~, ~someday~, ~delegated~, ~tickler~, ~habit~, ~knowledge~, ~quick-action~, ~trash~

*Example*: Only prompt for projects, auto-refile everything else:

#+begin_src emacs-lisp
(setq org-gtd-refile-prompt-for-types '(project-heading project-task))
#+end_src

*Example*: Add knowledge items to prompt list (they auto-refile by default):

#+begin_src emacs-lisp
(setq org-gtd-refile-prompt-for-types
      '(single-action project-heading project-task calendar
        someday delegated tickler habit knowledge))
#+end_src

See [[#controlling-refile-prompts][Controlling Refile Prompts by Item Type]] for detailed examples.

*** Mode-Line Configuration

**** ~org-gtd-mode-update-interval~

*Type*: Integer (seconds) or nil

*Default*: ~60~

*Description*: Seconds between automatic inbox count refreshes when ~org-gtd-mode~ is enabled.

The mode-line lighter (e.g., =GTD[5]=) updates automatically when Emacs redraws the mode-line. This setting controls an additional periodic refresh to catch external file changes (like mobile app syncs).

Values:
- Integer :: Refresh every N seconds
- ~nil~ :: Disable periodic refresh (count still updates on mode-line redraw)

*Example*: Refresh every 30 seconds:
#+begin_src emacs-lisp
(setq org-gtd-mode-update-interval 30)
#+end_src

*Example*: Disable periodic refresh:
#+begin_src emacs-lisp
(setq org-gtd-mode-update-interval nil)
#+end_src

**** ~org-gtd-mode-lighter-display~

*Type*: Symbol

*Default*: ~'always~

*Description*: Controls when the GTD lighter appears in the mode-line.

Values:
- ~'always~ :: Always show the lighter (e.g., =GTD[0]=, =GTD[5]=)
- ~'never~ :: Never show the lighter
- ~'when-non-zero~ :: Only show when inbox has items

*Example*: Hide lighter when inbox is empty:
#+begin_src emacs-lisp
(setq org-gtd-mode-lighter-display 'when-non-zero)
#+end_src

*Type*: Symbol or nil

*Default*: ~nil~

*Description*: Whether to show the organize types help buffer during clarification. This buffer displays all GTD item types with their keyboard shortcuts and brief descriptions, helping you decide how to categorize an item.

Values:

*Type*: Boolean

*Default*: ~nil~

*Description*: If non-nil, display project dependencies helper window when clarifying projects.

When enabled, shows a live view of task relationships in a side window when there are multiple tasks in the WIP buffer.

Useful for:
- Understanding complex dependency graphs
- Spotting cycles before they cause problems
- Planning parallel execution paths

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-clarify-display-helper-buffer t)
#+end_src

**** ~org-gtd-clarify-project-templates~

*Type*: Alist of (name . template) strings

*Default*: ~nil~

*Description*: Pre-defined project templates for common project types.

Each entry is a pair of (template-name . template-tasks) where template-tasks is a string of org headings to insert.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-clarify-project-templates
      '(("Blog Post" . "** Research topic\n** Write draft\n** Edit\n** Add images\n** Publish")
        ("Code Feature" . "** Design API\n** Write tests\n** Implement feature\n** Code review\n** Merge")))
#+end_src

*Entering newlines in templates*: When setting this variable in your configuration file, use ~\n~ for newlines as shown above. If entering template strings interactively (e.g., via ~M-x customize-variable~ or in the minibuffer), use ~C-q C-j~ to insert a literal newline character. This works on all platforms including Windows.

Use ~org-gtd-clarify-project-insert-template~ during clarification to insert a template.

**** ~org-gtd-clarify-duplicate-queue-position~

When you create duplicates during clarification, a side window appears showing pending duplicates. This variable controls where that window appears.

Values:
- ~'top~ :: Show queue window at top
- ~'bottom~ :: Show queue window at bottom
- ~'left~ :: Show queue window on left
- ~'right~ :: Show queue window on right

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-clarify-duplicate-queue-position 'right)
#+end_src

*See also*: [[#duplicating-items][Duplicating items during clarification]]

*** View Prefix Configuration

**** ~org-gtd-prefix-width~

*Type*: Integer

*Default*: ~12~

*Description*: Default width for the prefix column in org-gtd views.

The prefix shows context information (project name, area of focus, etc.) on the left side of each task. This variable sets the default width used when no explicit ~prefix-width~ is specified in a view spec.

Long values are truncated with ~org-gtd-agenda-truncate-ellipsis~ (default "…"). Short values are padded with spaces.

*Example*: Increase space for longer project names:
#+begin_src emacs-lisp
(setq org-gtd-prefix-width 20)
#+end_src

*Note*: You can also set ~prefix-width~ per-view in the View DSL. See [[#prefix-dsl][Prefix DSL]].

*Backward compatibility*: The old name ~org-gtd-engage-prefix-width~ still works but is deprecated.

**** ~org-gtd-agenda-truncate-ellipsis~

*Type*: String

*Default*: ~"…"~

*Description*: String appended when truncating long text in agenda prefixes.

The default ellipsis character (~…~) doesn't have consistent width across all fonts. Some fonts (like Iosevka) display it wider than one character, causing agenda items to misalign.

*Example*: Use ASCII dots for consistent alignment:
#+begin_src emacs-lisp
(setq org-gtd-agenda-truncate-ellipsis "...")
#+end_src

*Example*: Use a Braille character (works well in some fonts):
#+begin_src emacs-lisp
(setq org-gtd-agenda-truncate-ellipsis "⣀")
#+end_src

*See also*: ~org-gtd-prefix-width~ for controlling prefix column width.

*** Archive Configuration

**** ~org-gtd-archive-location~

*Type*: Function (zero arguments, returns string) or ~nil~

*Default*: ~#'org-gtd-archive-location-func~

*Description*: Archive location for org-gtd, or ~nil~ to use ~org-archive-location~.

When ~nil~, org-gtd uses org-mode's standard ~org-archive-location~ variable. This allows you to use your existing org-mode archive configuration with org-gtd.

When a function, calls it to get the archive location string. The returned string must match ~org-archive-location~ format.

Default function generates: =gtd_archive_YYYY.org::datetree/= (year-based archive files in ~org-gtd-directory~).

*Example*: Use org-mode's standard archive location:
#+begin_src emacs-lisp
;; Respect your org-archive-location setting
(setq org-gtd-archive-location nil)
;; Configure org-mode's archive as usual
(setq org-archive-location "archive.org::* Archived")
#+end_src

*Example*: Archive to a single file:
#+begin_src emacs-lisp
(defun my-archive-location ()
  "Archive to a single file."
  "archive.org::")

(setq org-gtd-archive-location #'my-archive-location)
#+end_src

*Example*: Archive to month-based files:
#+begin_src emacs-lisp
(defun my-monthly-archive ()
  "Archive to month-based files."
  (format "archive-%s.org::datetree/"
          (format-time-string "%Y-%m")))

(setq org-gtd-archive-location #'my-monthly-archive)
#+end_src

*** Missed Engagements Review Configuration

**** ~org-gtd-reflect-missed-custom-views~

*Type*: List of GTD view specifications

*Default*: ~nil~

*Purpose*: Create custom views to find specific types of missed engagements (e.g., only work-related items, only specific areas of focus).

Think of this like creating saved searches. Instead of seeing ALL missed items, you can create views that show only the ones relevant to a specific context.

*When to use*: If you have multiple areas of focus (Work, Home, Hobbies) and want to review each separately.

*Example - Area-Specific Reviews*:
#+begin_src emacs-lisp
(setq org-gtd-reflect-missed-custom-views
      '(((name . "Overdue Work Items")
         (area-of-focus . "Work")
         (deadline . past))
        ((name . "Missed Home Appointments")
         (area-of-focus . "Home")
         (type . calendar)
         (when . past))))
#+end_src

After configuring, run ~M-x org-gtd-reflect-missed-with-custom~ to see all standard views plus your custom ones.

*Backward compatibility*: The old variable name ~org-gtd-oops-custom-views~ still works but will be removed in a future version.

*** Advanced Item Configuration

**** ~org-gtd-user-types~

*Type*: Alist

*Default*: ~'()~

*Description*: Customize property prompts and input methods for built-in GTD types.

This alist allows you to override how org-gtd prompts for properties when organizing items. You can customize existing types but cannot add new ones.

Each entry is ~(TYPE-NAME . PLIST)~ where TYPE-NAME must be one of: ~next-action~, ~delegated~, ~calendar~, ~tickler~, ~someday~, ~project~, ~habit~, ~reference~, ~trash~, ~quick-action~.

*Property attributes you can set:*

| Attribute       | Description                                           |
|-----------------+-------------------------------------------------------|
| ~:prompt~       | The prompt string shown to the user                   |
| ~:input-fn~     | Custom function for input (overrides default prompt)  |
| ~:default~      | Default value (skips prompting if set)                |
| ~:type~         | Input type: ~text~, ~timestamp~, ~repeating-timestamp~|
| ~:required~     | Whether the property is required (~t~ or ~nil~)       |
| ~:org-property~ | The org-mode property name (string)                   |

*Example: Integrating Contact Managers with Delegation*

BBDB and EBDB are Emacs contact management packages. You can configure org-gtd to use completion from your contacts database when delegating tasks.

For EBDB integration:
#+begin_src emacs-lisp
;; Define function to complete from EBDB contacts
(defun my/ebdb-completing-read (prompt)
  "Read a contact name from EBDB with completion."
  (completing-read prompt
                   (mapcar (lambda (rec) (ebdb-record-name-string rec))
                           (ebdb-records))
                   nil t))

;; Configure delegation to use EBDB completion
(setq org-gtd-user-types
      '((delegated
         :properties
         ((:who :org-property "DELEGATED_TO" :type text :required t
                :prompt "Delegate to"
                :input-fn my/ebdb-completing-read)))))
#+end_src

For BBDB integration, use ~bbdb-records~ and ~bbdb-record-name~ instead:
#+begin_src emacs-lisp
(defun my/bbdb-completing-read (prompt)
  "Read a contact name from BBDB with completion."
  (completing-read prompt
                   (mapcar #'bbdb-record-name (bbdb-records))
                   nil t))
#+end_src

This pattern works for any completion source (org-contacts, custom databases, etc.).

*Example: Custom prompt text*

Change the default prompts without changing input behavior:
#+begin_src emacs-lisp
(setq org-gtd-user-types
      '((delegated
         :properties
         ((:who :org-property "DELEGATED_TO" :type text :required t
                :prompt "Assign to team member")
          (:when :org-property "ORG_GTD_TIMESTAMP" :type timestamp :required t
                 :prompt "Follow-up date")))))
#+end_src

*** Agenda Display Configuration

These variables control how properties are displayed in org-agenda views. When you run ~org-gtd-engage~ or other agenda commands, these settings determine what additional information appears alongside each task.

**** ~org-gtd-agenda-property-list~

*Type*: List of strings

*Default*: ~'("LOCATION")~

*Description*: Properties to display in agenda views.

When a task has any of these properties set, the value appears in the agenda line. Useful for showing context like location, delegated person, or custom metadata.

*Example*:
#+begin_src emacs-lisp
;; Show location and who tasks are delegated to
(setq org-gtd-agenda-property-list '("LOCATION" "DELEGATED_TO"))
#+end_src

**** ~org-gtd-agenda-property-position~

*Type*: Symbol

*Default*: ~'where-it-fits~

*Description*: Where properties appear relative to the agenda line.

Values:
- ~'same-line~ :: On the same line, starting at ~org-gtd-agenda-property-column~
- ~'next-line~ :: On the line below the task
- ~'where-it-fits~ :: Same line if it fits in the window, otherwise next line (default)

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-agenda-property-position 'next-line)
#+end_src

**** ~org-gtd-agenda-property-column~

*Type*: Integer

*Default*: ~60~

*Description*: Column position where properties start when using ~'same-line~ or ~'where-it-fits~ position.

Increase this if your task descriptions are long; decrease if you want properties closer to the task text.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-agenda-property-column 50)
#+end_src

**** ~org-gtd-agenda-property-separator~

*Type*: String

*Default*: ~"|"~

*Description*: Separator between multiple property values when a task has more than one property from ~org-gtd-agenda-property-list~.

*Example*:
#+begin_src emacs-lisp
(setq org-gtd-agenda-property-separator " · ")
#+end_src

*** Graph View Configuration

These variables control the project graph visualization feature.

**** ~org-gtd-graph-render-mode~

*Type*: Symbol

*Default*: ~'svg~

*Description*: Default rendering mode for project dependency graphs.

Values:
- ~'svg~ :: High-quality graphical rendering (requires GUI Emacs)
- ~'ascii~ :: Text-based rendering using box-drawing characters (works in terminal)

You can toggle between modes in any graph buffer by pressing ~v~.

*Example*:
#+begin_src emacs-lisp
;; Use ASCII mode by default (good for terminal users)
(setq org-gtd-graph-render-mode 'ascii)
#+end_src

*See also*: [[#graph-rendering-modes][Graph Rendering Modes]] for detailed comparison.

**** ~org-gtd-graph-ui-split-ratio~

*Type*: Float (0.0 to 1.0)

*Default*: ~0.7~

*Description*: Width ratio for the graph window when showing project graphs.

The graph view displays two panels: the dependency graph and a details panel showing the selected task. This ratio controls how much horizontal space the graph takes.

- ~0.7~ means the graph takes 70% of width, details take 30% (default)
- ~0.5~ would give equal space to both
- ~0.8~ would give more space to the graph

*Example*:
#+begin_src emacs-lisp
;; Give more space to the details panel
(setq org-gtd-graph-ui-split-ratio 0.6)
#+end_src

**** ~org-gtd-graph-sibling-mode~
:PROPERTIES:
:CUSTOM_ID: org-gtd-graph-sibling-mode
:END:

*Type*: Symbol

*Default*: ~'any-same-blocker~

*Description*: How to determine sibling tasks for TAB/S-TAB navigation in graph view.

When you press TAB or S-TAB in graph view, you move between "sibling" tasks. This variable controls what counts as a sibling:

Values:
- ~'any-same-blocker~ :: Tasks sharing at least one blocker (default). Two tasks are siblings if they have any blocker in common. This groups tasks that are conceptually related through shared prerequisites.
- ~'all-same-blockers~ :: Tasks with exactly the same set of blockers. Two tasks are siblings only if their blocker sets are identical. This is stricter and shows only tasks that are truly parallel alternatives.
- ~'dag-level~ :: Tasks at the same depth in the dependency graph. Two tasks are siblings if they have the same layer number, regardless of their actual blockers. This gives a visual/structural grouping.

*Example*:
#+begin_src emacs-lisp
;; Default: share any blocker
(setq org-gtd-graph-sibling-mode 'any-same-blocker)

;; Strict: exact same blockers only
(setq org-gtd-graph-sibling-mode 'all-same-blockers)

;; Structural: same depth in graph
(setq org-gtd-graph-sibling-mode 'dag-level)
#+end_src

*When to use each mode*:

- *any-same-blocker (default)*: Best for most users. When you're on "Write tests" and press TAB, you'll see other tasks that also depend on "Set up project"—tasks you could work on in parallel after finishing the blocker.

- *all-same-blockers*: Use when you want strict parallelism. Only shows tasks that are truly equivalent alternatives—same prerequisites, same position in the workflow.

- *dag-level*: Use when you think visually about your project. Groups all tasks at the same "layer" or depth, regardless of their actual dependencies.

*See also*: [[#graph-view-command-reference][Graph View Command Reference]] for navigation keybindings.

**** ~org-gtd-project-progress-cookie-position~
:PROPERTIES:
:CUSTOM_ID: org-gtd-project-progress-cookie-position
:END:

*Type*: Symbol or nil

*Default*: ~'end~

*Description*: Controls where progress cookies are displayed on project headings.

Values:
- ~nil~ :: Disabled (no cookies shown)
- ~'start~ :: After TODO keyword, before title
- ~'end~ :: After heading text, before tags (default)

Progress cookies show project completion as ~[completed/total][percent%]~ format, for example ~[3/7][42%]~.

Unlike org-mode's built-in statistics cookies (~[/]~ or ~[%]~) which count direct children, org-gtd's progress cookies correctly count all tasks linked to the project via ~ORG_GTD_PROJECT_IDS~, making them accurate for the DAG-based project structure.

*Example*:
#+begin_src emacs-lisp
;; Show cookies at end of heading (default)
(setq org-gtd-project-progress-cookie-position 'end)

;; Show cookies at start of heading
(setq org-gtd-project-progress-cookie-position 'start)

;; Disable progress cookies
(setq org-gtd-project-progress-cookie-position nil)
#+end_src

*What it looks like*:
#+begin_example
;; With 'end (default):
,* PROJ Buy a house [3/7][42%]                    :home:

;; With 'start:
,* PROJ [3/7][42%] Buy a house                    :home:

;; With nil:
,* PROJ Buy a house                               :home:
#+end_example

*Automatic updates*: Cookies are automatically recalculated when:
- Task TODO states change (via hook)
- Project is created
- ~org-gtd-projects-fix-all-todo-keywords~ is run
- ~org-gtd-project-update-all-cookies~ is called manually

*See also*: [[#project-progress-cookies][Project Progress Cookies]] for detailed usage, [[#org-gtd-project-update-all-cookies][~org-gtd-project-update-all-cookies~]] for manual refresh.

*** Reviewing Someday/Maybe Items
:PROPERTIES:
:CUSTOM_ID: someday-review
:END:

Someday/maybe items are the graveyard of dreams—or the incubator of future greatness. The difference? Regular review. This feature helps you stay connected to your possibilities without letting them become forgotten fossils.

*What is it*: A wizard-style workflow that shows you each someday item one at a time, letting you quickly defer it (keep for later) or clarify it (reactivate and make it actionable).

*Who needs it*: Anyone with someday/maybe items who wants to periodically review them during their GTD reflect process.

**** Your First Review in 60 Seconds

Try this right now:

1. Run ~M-x org-gtd-reflect-someday-review~
2. You'll see your first someday item in a read-only buffer
3. Press ~d~ to defer (keeps the item, logs that you reviewed it)
4. Or press ~c~ to clarify (reactivates the item)
5. Press ~q~ anytime to quit

That's it. You're reviewing your possibilities.

**** Understanding the Review Workflow

When you see a someday item during review, you're asking yourself one question: "Is now the time to pursue this?"

#+begin_example
Someday item: "Learn to play piano"

Is now the time?
  YES → Press 'c' (clarify) → Item becomes active, you organize it fresh
  NO  → Press 'd' (defer) → Item stays in someday, with timestamp logged
#+end_example

*Why defer logs a timestamp*: The LOGBOOK entry creates a history. During future reviews, you can see how long items have been sitting. An item deferred 50 times over 3 years might be ready to trash—or finally pursue.

**** Tutorial: Weekly Someday Review

Here's how to incorporate this into your weekly review:

*Basic flow*:
#+begin_example
M-x org-gtd-reflect-someday-review

For each item:
- Read it
- Decide: defer or clarify?
- Press d or c
- Repeat until "Review complete"
#+end_example

*What happens when you clarify*:
1. The item's previous state is restored (if it was a delegated action, it remembers the delegate)
2. You go through the organize flow
3. After organizing, review automatically continues with the next item

*What happens when you defer*:
1. A "Reviewed [timestamp]" entry is added to the item's LOGBOOK
2. Review advances to the next item
3. The item stays in someday/maybe

**** Organizing Your Someday Items (Optional)

If your someday list grows large, you can group items into named lists:

#+begin_src elisp
;; Optional: Define someday lists for focused reviews
(setq org-gtd-someday-lists '("Work Ideas" "Personal Projects" "Learning" "Travel"))
#+end_src

With this configured:

1. *When organizing items as someday*: You'll be prompted to choose a list
2. *When reviewing*: You'll be prompted which list to review (or "Unassigned")
3. *Programmatic access*: Call ~(org-gtd-reflect-someday-review "Work Ideas")~ directly

This is entirely optional. Without configuration, all someday items are reviewed together.

**** Common Patterns

*Monthly Deep Review*:
#+begin_example
;; Review everything, no list filter
M-x org-gtd-reflect-someday-review

;; Go through each item thoughtfully
;; This might take 15-30 minutes for 50 items
#+end_example

*Focused Category Review*:
#+begin_example

M-x org-gtd-reflect-someday-review → "Learning"

;; Only see learning-related someday items
#+end_example

*Finding Stale Items*:
Look at items during review that have many LOGBOOK entries spanning years. Ask yourself: "Am I ever actually going to do this?" If not, trash it. If yes, this might be the time to clarify it.

*** Reflect Commands (Missed Engagements)

**** What Are Missed Engagements?

Life doesn't go as planned. You miss appointments, delegated items slip through cracks, projects run late. These aren't failures—they're normal. What matters is catching them and deciding what to do next.

The missed engagements review helps you find three types of items that need attention:
- *Appointments you missed*: Calendar items with dates in the past
- *Check-ins you forgot*: Delegated items where follow-up dates passed
- *Projects running late*: Projects with overdue deadlines or start dates

This is your safety net. Run it daily or weekly to ensure nothing falls through the cracks.

**** Your First Review in 30 Seconds

Try this right now:

1. Run ~M-x org-gtd-reflect-missed-engagements~
2. Look at what appears in the agenda view
3. Press ~TAB~ on any item to see its details

That's it. You're now reviewing missed engagements.

If you see items, ask yourself: "What should I do about this now?" Then organize accordingly (reschedule, cancel, or act).

**** Understanding the Review Workflow

Think of GTD like a promise system. When you:
- Schedule an appointment → you promise to be there at that time
- Delegate a task → you promise to check in on the date you set
- Set a project deadline → you promise to complete by that date

When dates pass without action, you've broken a promise (to yourself or others).

The review workflow helps you:
1. *Find* broken promises (missed engagements)
2. *Decide* what to do about them
3. *Act* on your decision

This isn't about guilt—it's about staying in control.

**** Tutorial: Daily Review Workflow

Here's how to use this in your daily routine:

*Morning Review* (2 minutes):
#+begin_example
M-x org-gtd-reflect-missed-engagements

Look at each item:
- Missed appointment? Reschedule or apologize
- Forgot to check in on delegation? Do it now
- Project running late? Decide: extend deadline or cancel
#+end_example

*Focusing on One Type*:

If you just want to see missed appointments:
#+begin_example
M-x org-gtd-reflect-missed-calendar
#+end_example

Or just delegated items needing check-ins:
#+begin_example
M-x org-gtd-reflect-missed-delegated
#+end_example

Or just late projects:
#+begin_example
M-x org-gtd-reflect-missed-projects
#+end_example

Each command shows only that type, making it easier to focus.

**** Common Patterns

*Pattern 1: Morning Triage*
Start each day by reviewing missed engagements. Handle or reschedule everything before starting new work.

*Pattern 2: Weekly Cleanup*
During weekly review, run the full missed engagements view. This catches anything that slipped through daily reviews.

*Pattern 3: Context-Specific Review*
Use custom views to see missed items by area of focus (see configuration below).

*** Reflect Commands (Upcoming Delegated)

**** What Are Upcoming Delegated Check-ins?

You delegate work and set check-in dates. Some people finish early. Others appreciate regular check-ins. Waiting until check-in dates pass means lost opportunities.

The upcoming delegated review shows all active delegated items with future check-in dates. This helps you:
- *Catch early completions*: Someone finished early, you can adjust the plan now
- *Plan your follow-ups*: See what check-ins are coming this week or month
- *Proactive management*: Reach out before problems develop

This is your planning tool. Use it weekly to prepare your delegation check-ins, or ad-hoc when people report early progress.

**** Your First Review in 30 Seconds

Try this right now:

1. Run ~M-x org-gtd-reflect-upcoming-delegated~
2. Look at the delegated items with future check-in dates
3. Press ~TAB~ on any item to see when the check-in is scheduled

That's it. You're now seeing upcoming delegation check-ins.

If someone tells you they finished early, you'll find that item here and can update your plans accordingly.

**** Understanding Proactive Delegation Management

Think about delegation timing:

*Reactive management* (missed engagements):
- Check-in date passes → you remember to follow up
- Problem discovered after it's late
- Always catching up

*Proactive management* (upcoming review):
- See check-ins coming this week → prepare questions
- Someone finishes early → immediately unblock dependent work
- Stay ahead of problems

The upcoming delegated review shifts you from reactive to proactive.

**** Tutorial: Weekly Planning Workflow

Here's how to use this in your weekly planning:

*Sunday Planning* (5 minutes):
#+begin_example
M-x org-gtd-reflect-upcoming-delegated

For each item:
- Check-in this week? Prepare questions or schedule call
- Might finish early? Be ready to adjust plans
- Blocked on something? Follow up proactively
#+end_example

*When Someone Reports Early Completion*:
#+begin_example
M-x org-gtd-reflect-upcoming-delegated

Press TAB to jump to the item
Mark it DONE (it disappears from the upcoming view)
Check if this unblocks other work in the project
#+end_example

The first shows what you missed. The second shows what's coming. Together they give complete delegation visibility.

**** Common Patterns

*Pattern 1: Weekly Planning*
Every Sunday or Monday, review upcoming delegated items for the week. Know what check-ins are coming so you're prepared.

*Pattern 2: Early Completion Response*
When someone says "I finished that task you gave me," pull up this view to find it quickly and update your plans.

*Pattern 3: Project Acceleration*
Review a specific project's delegated items. If anyone finished early, immediately reassign work to take advantage of the extra time.

*Pattern 4: Delegation Optimization*
Notice patterns: Who consistently finishes early? Give them more work. Who's always late? More frequent check-ins.

**** Understanding What You See

The view shows all active (not done) delegated items with future check-in dates:
- Items with TODO, NEXT, or WAIT states
- Items with check-ins far in the future (months away)
- Items from all areas of focus

Once you mark an item DONE or CNCL, it disappears from this view automatically—you've already processed it and taken action.

If you see too many items and want to filter:
- Focus on one project at a time (use project-specific review)
- Look at specific timeframes (future enhancement—not yet implemented)
- Use custom views with area-of-focus filters

*** Custom View Commands

**** ~org-gtd-view-show~

**What it is:** Create custom GTD agenda views using a declarative language instead of learning org-agenda skip function internals.

**Why you'd use it:** The built-in views (engage, review-stuck-projects, etc.) cover common needs, but you have unique workflows. Maybe you only want to see work-related NEXT actions, or projects in a specific area, or items tagged "urgent". This lets you create exactly the view you need.

**Who needs it:** Users who want views tailored to their specific workflow beyond the built-in commands.

**Your first custom view (5 minutes):**

Let's create a view showing only your NEXT actions (no calendar, no agenda).

1. Add this to your config file:
   #+begin_src emacs-lisp
   (defun my-next-actions ()
     "Show all NEXT actions in a simple list."
     (interactive)
     (org-gtd-view-show
      '((name . "All NEXT Actions")
        (type . next-action))))
   #+end_src

2. Save and reload your config (~M-x eval-buffer~ or restart Emacs)

3. Run it:
   #+begin_example
   M-x my-next-actions
   #+end_example

You'll see all your NEXT actions in one list. That's it—you've created a custom view!

**Understanding how views work:**

Think of views like filtered searches. You tell org-gtd what to show, and it finds matching items.

The built-in ~org-gtd-engage~ command? It uses ~org-gtd-view-show~ internally. ~org-gtd-reflect-stuck-projects~? Same thing. You're now using the same tool the package uses to create its own views.

View specs are simple: give it a ~name~ and add filters. Filters are pairs like ~(filter-type . value)~. Multiple filters combine with AND logic—all must match.

#+begin_src emacs-lisp
;; Simple view spec
'((name . "Delegated Items")
  (type . delegated))
#+end_src

The most common filter is ~type~, which matches GTD item types: ~project~, ~next-action~, ~calendar~, ~delegated~, ~tickler~, ~someday~, ~habit~, ~stuck-project~, ~completed-project~.

**Tutorial: Common custom views**

*Show only work-related NEXT actions:*

#+begin_src emacs-lisp
(defun my-work-next-actions ()
  "Show NEXT actions for work projects only."
  (interactive)
  (org-gtd-view-show
   '((name . "Work NEXT Actions")
     (type . next-action)
     (area-of-focus . "Work"))))
#+end_src

Two filters: must be a next-action AND must be in Work area.

*Show projects that are stuck:*

#+begin_src emacs-lisp
(defun my-stuck-projects ()
  "Show projects with no NEXT actions."
  (interactive)
  (org-gtd-view-show
   '((name . "Stuck Projects")
     (type . stuck-project))))
#+end_src

One filter: type must be stuck-project (built-in type that checks for stuck state).

*Show delegated items due today:*

#+begin_src emacs-lisp
(defun my-delegated-today ()
  "Show delegated items with check-ins due today."
  (interactive)
  (org-gtd-view-show
   '((name . "Delegated Check-ins Today")
     (type . delegated)
     (when . today))))
#+end_src

The ~when~ filter uses semantic time: ~today~, ~past~, or ~future~. It automatically knows that for delegated items, "when" means the ~ORG_GTD_TIMESTAMP~ property.

*Show multiple related views together:*

#+begin_src emacs-lisp
(defun my-morning-review ()
  "Show morning planning views: NEXT actions and calendar."
  (interactive)
  (org-gtd-view-show
   '(((name . "Today's NEXT Actions")
      (type . next-action))
     ((name . "Delegated Items to Follow Up")
      (type . delegated)
      (when . today)))))
#+end_src

This shows TWO views in one agenda: NEXT actions first, then delegated items due today.

*Filter by type (most common):*
#+begin_src emacs-lisp
(type . project)          ; All projects
(type . next-action)      ; Single actions (with NEXT keyword)
(type . delegated)        ; Delegated items (with WAIT keyword)
(type . calendar)         ; Calendar items
(type . tickler)          ; Tickler items (time-based reminders)
(type . someday)          ; Someday/maybe items
(type . habit)            ; Habits
(type . stuck-project)    ; Projects needing attention
(type . completed-project) ; Projects ready to archive
#+end_src

*Filter by semantic time (~when~):*
#+begin_src emacs-lisp
(when . today)            ; Items due today
(when . past)             ; Missed items
(when . future)           ; Upcoming items
#+end_src

The ~when~ filter automatically uses the right timestamp property for each type:
- For ~delegated~ and ~calendar~: checks ~ORG_GTD_TIMESTAMP~
- For ~tickler~: checks the tickler review date

*Filter by area of focus:*
#+begin_src emacs-lisp
(area-of-focus . "Work")
#+end_src

*Combine multiple filters (AND logic):*
#+begin_src emacs-lisp
'((name . "Overdue Work Projects")
  (type . project)
  (area-of-focus . "Work")
  (deadline . past))
;; Shows: Projects AND Work area AND overdue
#+end_src

**When to create custom views:**

Create a custom view when you find yourself:
- Repeatedly filtering the engage view manually
- Wanting to see specific combinations org-gtd doesn't provide
- Needing views for specific contexts (home office, traveling, morning routine)
- Organizing weekly reviews around specific categories

Don't create views for one-time queries—just use the built-in views and navigate. Create views for repeated patterns in your workflow.

**Using Multiple Concurrent Views:**

By default, calling ~org-gtd-view-show~ multiple times replaces the previous agenda buffer. To display multiple views simultaneously:

1. Enable sticky agenda buffers:
   #+begin_src emacs-lisp
   (setq org-agenda-sticky t)
   #+end_src

2. Pass different KEYS to each call:
   #+begin_src emacs-lisp
   (defun my-dashboard ()
     "Show my GTD dashboard with multiple views."
     (interactive)
     (delete-other-windows)
     (org-gtd-view-show '((name . "Next Actions") (type . next-action)) "a")

     (other-window 1)

Each view will appear in its own buffer: ~*Org Agenda(a)*~, ~*Org Agenda(c)*~, etc.

**** Updating Items Without Refiling

**What this is:** A way to reconfigure existing GTD items (change their category, properties, or details) without moving them to a different location in your files.

**Who needs it:** Anyone who wants to change how an item is organized while keeping it where it is - perfect for items already in projects, or when you like your current file organization.

**Your first use (30 seconds):**

You're looking at your agenda and see a single action that should actually be delegated. But it's already in a specific project file and you want it to stay there:

1. In agenda view, put point on the item
2. Type: ~C-u M-x org-gtd-clarify-agenda-item~
3. Make your changes in the clarify buffer
4. Type: ~M-x org-gtd-organize~
5. Type: ~-n~ to toggle "Update in place (no refile)"
6. Choose: ~d~ for Delegate
7. Fill in delegation details
8. Done - item is updated but stays in its current location

**How it works:**

Normally when you organize an item, org-gtd moves (refiles) it to the appropriate GTD type location. But sometimes you want to change the configuration without moving the item.

There are two ways to trigger this:

*Via prefix argument:*
- ~C-u M-x org-gtd-clarify-item~ - Clarify item at point without refiling
- ~C-u M-x org-gtd-clarify-agenda-item~ - Clarify agenda item without refiling

*Via transient toggle:*
- During organization, press ~-n~ in the ~org-gtd-organize~ menu to toggle "Update in place (no refile)"
- The toggle is only available when NOT processing the inbox (inbox items must be refiled)

When the skip-refile flag is set, organizing the item will:
- Apply all the same configuration (properties, tags, hooks)
- Update the item in its current location
- NOT move it to a different file or heading

**Common scenarios:**

*Reconfiguring project tasks:*
- Task is already in the right project file
- You want to change it from single action to delegated
- Use skip-refile to update without moving

*Adjusting agenda items:*
- Item appears in your daily agenda
- You realize it needs different properties (change deadline, add delegation, etc.)
- Use skip-refile to update configuration in place

*Organizing items in custom locations:*
- You've organized items in a specific way outside ~org-gtd-directory~
- You want to apply GTD types but preserve your file structure
- Use skip-refile to maintain your organization

**What stays the same vs what changes:**

*Changes applied:*
- GTD type (ORG_GTD property)
- TODO keyword state
- Properties (delegation info, dates, etc.)
- Tags
- All organize hooks

*Preserved:*
- File location
- Position within file
- Parent heading (for tasks in projects)
- Sibling relationships

**Technical details:**

When you set the skip-refile flag (via ~C-u~ prefix or ~-n~ toggle):
- The flag is stored in the clarify buffer as ~org-gtd-clarify--skip-refile~
- Category finalize functions check this flag
- If set, they call ~org-gtd-organize--update-in-place~ instead of refiling
- The original heading is replaced with the configured content from the WIP buffer
- Archive categories (quick-action, knowledge, trash) always archive regardless of this flag

**Migration note:**

In previous versions, there was a special command ~org-gtd-delegate-item-at-point~ for delegating items without moving them. This command has been removed in favor of the more general skip-refile mechanism:

*OLD way (no longer available):*
#+begin_src emacs-lisp
M-x org-gtd-delegate-item-at-point
#+end_src

*NEW way (version 4.0+):*
#+begin_src emacs-lisp
;; From agenda or file:
C-u M-x org-gtd-clarify-item
;; or
C-u M-x org-gtd-clarify-agenda-item
;; Then organize and press -n toggle
M-x org-gtd-organize
;; Press -n to enable skip-refile
;; Choose delegation
#+end_src

The new approach is more flexible - it works for ANY GTD type, not just delegation.

** Properties Reference (Internal Implementation)
:PROPERTIES:
:DESCRIPTION: All org properties used by org-gtd
:CUSTOM_ID: properties-reference
:END:

*For most users*: You don't need to read this section! Use the graph view or text-based task management commands instead.

*This section is for*:
- Understanding org-gtd's internal data model
- Writing elisp automation/integration code
- Debugging edge cases
- Migrating data from other systems

org-gtd uses org-mode properties to track state and relationships. These properties are managed automatically by org-gtd commands - *you should not edit them manually during normal use.*

If you find yourself manually editing properties, that indicates a missing feature - please file an issue!

*** Core GTD Properties

**** ORG_GTD

*Used on*: All GTD items (projects, actions, calendar items, tickler items, etc.)

*Purpose*: Identifies the type of GTD item

*Values*:
- ~"Projects"~ :: Project heading
- ~"Actions"~ :: Project tasks and single actions
- ~"Calendar"~ :: Calendar items (appointments, deadlines)
- ~"Tickler"~ :: Items with specific review dates (time-based reminders)
- ~"Someday"~ :: Someday/maybe items (no specific timeframe)
- ~"Delegated"~ :: Delegated tasks (set in combination with DELEGATED_TO)

*Example*:
#+begin_example
,* My Project
:PROPERTIES:
:ORG_GTD: Projects
:END:
,** NEXT Task 1
:PROPERTIES:
:ORG_GTD: Actions
:END:
#+end_example

*Note*: This property is how org-gtd identifies items. Don't modify manually unless you understand the implications.

**** ORG_GTD_REFILE

*Used on*: Category headings that serve as refile targets

*Purpose*: Marks a heading as a refile target for org-gtd's optional refile system (see [[#refiling-after-organizing][Refiling section]])

*Values*:
- ~"Projects"~ :: Target for refiling projects
- ~"Actions"~ :: Target for refiling single actions
- ~"Calendar"~ :: Target for refiling calendar items
- ~"Tickler"~ :: Target for refiling tickler items (time-based reminders)
- ~"Someday"~ :: Target for refiling someday/maybe items
- ~"Habits"~ :: Target for refiling habits

*Multivalue support*: Values can be space-separated to accept multiple types. For example, ~Actions Projects~ makes a heading a valid target for both single actions and projects.

*Example*:
#+begin_example
,* Projects         <-- Can be at any level in any file
:PROPERTIES:
:ORG_GTD_REFILE: Projects
:END:

,* Work/Development Projects   <-- Can have multiple targets per type
:PROPERTIES:
:ORG_GTD_REFILE: Projects
:END:

,* Work Tasks      <-- Accepts multiple types
:PROPERTIES:
:ORG_GTD_REFILE: Actions Projects
:END:
#+end_example

*How it's set*:
- Automatically created by ~org-gtd-upgrade-v3-to-v4~ (renames ORG_GTD on level 1 headings)
- Manually when creating custom refile targets
- Via ~org-entry-put~ in elisp: ~(org-entry-put nil "ORG_GTD_REFILE" "Projects")~

*Important notes*:
- Org-gtd merges these targets with your ~org-refile-targets~ configuration
- Can exist at ANY level in ANY file in ~org-agenda-files~
- You can have multiple refile targets for the same category type
- A single heading can accept multiple types (space-separated values)
- Your ~org-refile-targets~ appear first, then ~ORG_GTD_REFILE~ targets

*** Project Properties

**** ORG_GTD_FIRST_TASKS

*Used on*: Project headings

*Purpose*: Identifies which tasks can start immediately (have no dependencies)

*Format*: Space-separated list of task IDs

*Example*:
#+begin_example
,* Software Release
:PROPERTIES:
:ORG_GTD: Projects
:ORG_GTD_FIRST_TASKS: abc123 def456
:END:
#+end_example

This means tasks with IDs "abc123" and "def456" can both start immediately (parallel execution).

*How it's set*:
- Automatically when organizing a project
- Automatically by graph view ~r~ (add root task) and ~b~ (add blocker as root)
- Programmatically via ~org-entry-add-to-multivalued-property~

*For interactive use*: Use graph view commands instead of editing this property directly.

*** Task Dependency Properties

**** ORG_GTD_DEPENDS_ON

*Used on*: Project tasks

*Purpose*: Lists task IDs that must complete before this task can start

*Format*: Space-separated list of task IDs

*Example*:
#+begin_example
,** NEXT Get project approval
:PROPERTIES:
:ID: task-001
:ORG_GTD: Actions
:ORG_GTD_BLOCKS: task-002 task-003
:END:
,** TODO Design solution
:PROPERTIES:
:ID: task-002
:ORG_GTD: Actions
:ORG_GTD_DEPENDS_ON: task-001
:ORG_GTD_BLOCKS: task-004
:END:
,** TODO Setup infrastructure
:PROPERTIES:
:ID: task-003
:ORG_GTD: Actions
:ORG_GTD_DEPENDS_ON: task-001
:ORG_GTD_BLOCKS: task-004
:END:
,** TODO Implement feature
:PROPERTIES:
:ID: task-004
:ORG_GTD: Actions
:ORG_GTD_DEPENDS_ON: task-002 task-003
:END:
#+end_example

In this example:
- Task 001 (approval) starts first
- Tasks 002 (design) and 003 (infrastructure) can run in parallel after approval
- Task 004 (implement) waits for both 002 and 003 to complete

*How it's set*:
- Graph view: ~s~ (add successor), ~b~ (add blocker), ~B~ (modify blockers)
- Text commands: ~org-gtd-task-add-blockers~, ~org-gtd-task-add-dependent~
- Programmatically: ~org-gtd-dependencies-create~ (maintains bidirectional relationships)

*For interactive use*: Use graph view or text-based task commands instead of editing this property directly.

**** ORG_GTD_BLOCKS

*Used on*: Project tasks

*Purpose*: Lists task IDs that depend on this task completing (inverse of DEPENDS_ON)

*Format*: Space-separated list of task IDs

*Relationship*: If task A has ~ORG_GTD_BLOCKS: B C~, then:
- Task B should have ~ORG_GTD_DEPENDS_ON: A~
- Task C should have ~ORG_GTD_DEPENDS_ON: A~

*How it's set*:
- Automatically maintained when setting ORG_GTD_DEPENDS_ON (bidirectional)
- Programmatically via ~org-gtd-dependencies-create~ (handles bidirectional updates)

*For interactive use*: Use graph view or text-based task commands - they maintain the bidirectional relationship automatically.

**** ORG_GTD_PROJECT_IDS

*Used on*: Tasks

*Purpose*: Lists project IDs this task belongs to (supports multi-project tasks)

*Format*: Space-separated list of project IDs

*Note*: Currently org-gtd creates one project per task, but this property supports future multi-project features.

*** Calendar and Time Properties

**** ORG_GTD_TIMESTAMP

*Used on*: Calendar items, delegated items

*Purpose*: Stores the appointment time or follow-up date

*Format*: Org timestamp (inactive timestamp)

*Example*:
#+begin_example
,* Doctor appointment
:PROPERTIES:
:ORG_GTD: Calendar
:ORG_GTD_TIMESTAMP: [2025-10-15 Wed 14:00]
:END:
#+end_example

*Why not use SCHEDULED*: org-gtd uses a custom property to distinguish between "do this at this time" (GTD calendar items) and "start working on this sometime after this date" (org-mode scheduling).

*How it's set*:
- Automatically by ~org-gtd-organize~ when organizing items as calendar items
- Programmatically when creating calendar items

*For interactive use*: Use ~org-gtd-organize~ to change calendar items.

*** Delegation Properties

*Used on*: Delegated items

*Purpose*: Stores the name of person/team the task is delegated to

*Format*: String (person's name)

*Example*:
#+begin_example

*** Area of Focus Properties

*Used on*: All items (when using areas of focus)

*** Standard Org Properties Used by org-gtd

**** ID

*Used on*: All GTD items

*Purpose*: Unique identifier for the item (org-mode standard)

*Format*: Auto-generated UUID

*Note*: org-gtd relies heavily on IDs for task relationships. Don't delete ID properties.

**** TODO keyword

*Not a property, but a heading keyword*

*Values used by org-gtd*:
- Value from ~org-gtd-keyword-mapping~'s ~todo~ key (default "TODO")
- Value from ~org-gtd-keyword-mapping~'s ~next~ key (default "NEXT")
- Value from ~org-gtd-keyword-mapping~'s ~wait~ key (default "WAIT")
- Value from ~org-gtd-keyword-mapping~'s ~done~ key (default "DONE")
- Value from ~org-gtd-keyword-mapping~'s ~canceled~ key (default "CNCL")

*Used on*: Habits primarily

*Purpose*: For org-mode habits, defines repeat pattern

*Note*: org-gtd uses ORG_GTD_TIMESTAMP for calendar items instead of SCHEDULED to maintain GTD semantics.

**** DEADLINE (org-mode standard)

*Used on*: Items with hard deadlines

*Purpose*: Mark items that must be done by a specific date

*Note*: org-gtd respects org-mode deadlines in all views and oops checks.

** Troubleshooting Projects
:PROPERTIES:
:DESCRIPTION: How to fix project dependency problems
:CUSTOM_ID: troubleshooting-projects
:END:

This section covers how to fix problems with project dependencies. *You should rarely need this* - the graph view and task management commands handle dependencies correctly. If you find yourself needing these troubleshooting steps frequently, that indicates a bug - please file an issue!

*** Fixing Broken Dependencies

If you encounter dependency problems (circular dependencies, broken references, orphaned tasks):

1. *Validate project structure*:
   - Put point on project heading
   - Run ~M-x org-gtd-validate-project-dependencies~
   - This detects broken references, orphaned tasks, and circular dependencies
   - Follow the guidance provided

2. *Visual inspection with graph view*:
   - Run ~M-x org-gtd-show-project-graph~
   - Visual inspection often makes problems obvious
   - Missing arrows? Use ~s~ to add successor or ~B~ to add blockers
   - Wrong arrows? Use ~B~ or ~S~ to uncheck incorrect relationships
   - Use ~i~ to inspect a task's current relationships

3. *Clear and rebuild*:
   If task relationships are completely corrupted:
   - In graph view: Select task, use ~B~ and ~S~ to adjust blockers/dependents
   - Or in text: Run ~M-x org-gtd-task-clear-relationships~
   - Rebuild using graph view: ~s~ (add successor), ~b~ (add blocker)

*** When Manual Property Editing is Needed

*You should never need to manually edit properties during normal use.*

The ONLY cases where manual property editing might be necessary:

1. *Writing elisp automation/integration code*
   - See [[#properties-reference][Properties Reference]] for property documentation
   - Use programmatic functions: ~org-gtd-dependencies-create~, ~org-entry-add-to-multivalued-property~, etc.
   - Never manipulate properties directly from interactive commands

2. *Debugging org-gtd internals*
   - If you suspect a bug in org-gtd's property management
   - Compare properties with graph view to identify discrepancies
   - File an issue with details!

3. *Migrating data from another system*
   - If importing projects from external tools
   - Batch property updates may be more efficient
   - Validate with ~org-gtd-validate-project-dependencies~ afterward

4. *Emergency recovery from data corruption*
   - Only as last resort if graph view and commands fail
   - After manual edits, run ~org-gtd-projects-fix-todo-keywords-for-project-at-point~ (one project)
   - Or run ~org-gtd-projects-fix-all-todo-keywords~ to fix all projects at once
   - Consider this a bug and file an issue

*If you find yourself manually editing properties regularly*, that indicates missing features. Please file an issue describing your workflow - we'll add the missing commands!

*** Common Problems and Solutions

**** Project Shows No NEXT Tasks (Stuck Project)

*Symptom*: Project has incomplete tasks but none are NEXT.

*Diagnosis*:
- Run ~M-x org-gtd-show-project-graph~
- Look for blue boxes (NEXT tasks)
- If no blue boxes, check for:
  - Circular dependencies (arrows forming a loop)
  - All tasks waiting on incomplete tasks
  - Missing ORG_GTD_FIRST_TASKS property

*Solution*:
- Fix circular dependencies: Use ~B~ to remove incorrect blocker relationships
- Add root tasks: Use ~r~ to create tasks that can start immediately
- Run ~org-gtd-validate-project-dependencies~ for detailed diagnosis

**** Too Many NEXT Tasks

*Symptom*: Project shows 10+ blue boxes in graph view.

*Diagnosis*: Tasks that should be dependent are independent.

*Solution*:
- In graph view, identify tasks that should depend on others
- Select a task, use ~B~ to add blockers it should wait for
- Or use ~s~ from an earlier task to add a successor that should come later

**** Task Won't Advance to NEXT

*Symptom*: Completed a task, but dependent task still shows TODO (orange).

*Diagnosis*:
- In graph view, select the orange task
- Press ~i~ to show relationships
- Check if all blockers are actually DONE

*Solution*:
- If blockers are DONE but showing as blocking: Press ~g~ to refresh graph
- If blocker shouldn't block this task: Use ~B~ to modify blockers and uncheck it
- If many wrong dependencies: Run ~org-gtd-task-clear-relationships~, rebuild with ~s~/~b~

**** Task States Inconsistent After External Edits

*Symptom*: After editing on mobile app or resolving sync conflicts, task states don't match dependencies.

*Examples*:
- Tasks marked NEXT but blocked by incomplete dependencies
- Tasks stuck in TODO when they should be NEXT
- Multiple projects showing inconsistent states

*Diagnosis*:
- External tools (mobile apps, web interfaces) don't understand org-gtd dependency logic
- Manual edits or sync conflicts disrupted task states
- Affects all projects if you edited multiple files

*Solution*:
- For one project: Put point on project heading, run ~M-x org-gtd-projects-fix-todo-keywords-for-project-at-point~
- For all projects: Run ~M-x org-gtd-projects-fix-all-todo-keywords~

*Recommended workflow after mobile edits*:
1. Sync files to Emacs
2. Run ~M-x org-gtd-projects-fix-all-todo-keywords~
3. Verify with ~M-x org-gtd-engage~ - should show correct NEXT tasks

** View DSL Filter Reference
:PROPERTIES:
:DESCRIPTION: Complete reference for the View DSL
:CUSTOM_ID: view-dsl-reference
:END:

Build custom agenda views in minutes. The View DSL lets you filter your GTD items by type, time, area of focus, and more---using simple declarative syntax instead of writing skip functions.

*For:* GTD users who want views beyond the built-in ~org-gtd-engage~ and ~org-gtd-reflect-*~ commands.

*** Your First Custom View in 60 Seconds

Try this now:

1. Evaluate this code (select it and run ~M-x eval-region~):

   #+begin_src emacs-lisp
   (org-gtd-view-show
    '((name . "My Delegated Items")
      (type . delegated)))
   #+end_src

2. An agenda view appears showing all your delegated items

3. Try changing ~delegated~ to ~next-action~ and re-evaluate---now you see NEXT actions

That's it. You just created a custom view. The rest of this section shows you what else you can filter by.

*** Understanding View Specs

A view spec is a simple list describing what you want to see:

#+begin_src emacs-lisp
'((name . "View Name")     ;; What appears in the agenda header
  (type . delegated)       ;; Filter: show only delegated items
  (when . past))           ;; Filter: only items with past dates
#+end_src

*Mental model:* Think of each line as a filter. Items must pass ALL filters to appear.  ~(type . delegated)~ means "only delegated items". Adding ~(when . past)~ means "only delegated items whose check-in date has passed".

**** Combining Filters

Filters stack with AND logic:

#+begin_src emacs-lisp
;; Delegated items + past due = missed check-ins
'((name . "Missed Check-ins")
  (type . delegated)
  (when . past))

;; Projects + specific area = focused view
'((name . "Work Projects")
  (type . active-project)
  (area-of-focus . "Work"))
#+end_src

**** Multi-Block Views

Show multiple filtered lists in one view:

#+begin_src emacs-lisp
'((name . "My Dashboard")
  (blocks . (((name . "Calendar Today")
              (type . calendar)
              (when . today))
             ((name . "Delegated Due")
              (type . delegated)
              (when . past))
             ((name . "NEXT Actions")
              (type . next-action)))))
#+end_src

Each block is its own filter. The view shows them stacked as separate sections.

*** Common Patterns

**** Weekly Review View

See what needs attention:

#+begin_src emacs-lisp
(defun my-weekly-review ()
  "Show stuck projects, missed items, and recent completions."
  (interactive)
  (org-gtd-view-show
   '(((name . "Stuck Projects")
      (type . stuck-project))
     ((name . "Missed Delegated")
      (type . delegated)
      (when . past))
     ((name . "Completed This Week")
      (done . past-week)))))
#+end_src

**** Morning Planning View

Start your day focused:

#+begin_src emacs-lisp
(defun my-morning-view ()
  "Calendar, delegated check-ins, and NEXT actions."
  (interactive)
  (org-gtd-view-show
   '((name . "Morning Planning")
     (blocks . (((name . "Today's Schedule")
                 (block-type . calendar-day))
                ((name . "Check-ins Due")
                 (type . delegated)
                 (when . today))
                ((name . "Ready to Work On")
                 (type . next-action)))))))
#+end_src

**** Area of Focus View

Filter everything by life area:

#+begin_src emacs-lisp
(defun my-work-view ()
  "All work-related active items."
  (interactive)
  (org-gtd-view-show
   '(((name . "Work Projects")
      (type . active-project)
      (area-of-focus . "Work"))
     ((name . "Work NEXT Actions")

      (area-of-focus . "Work"))
     ((name . "Work Delegated")
      (type . delegated)
      (area-of-focus . "Work")))))
#+end_src

*** Filter Reference

The following sections document all available filters. Use them to build the exact view you need.

**** View Structure

A GTD view is defined as an alist with filters at the top level:

#+begin_src emacs-lisp
;; Simple view with filters at top level
'((name . "View Name")
  (type . delegated)
  (when . past))
#+end_src

Multiple filters create AND logic (all must match).

***** Multi-Block Views

For complex views with multiple sections (like the engage view), use ~blocks~:

#+begin_src emacs-lisp
'((name . "My Custom Dashboard")
  (blocks . (((name . "Today's Calendar")
              (block-type . calendar-day))
             ((name . "Items Due Today")
              (type . delegated)
              (when . today))
             ((name . "All NEXT Actions")
              (type . next-action)))))
#+end_src

Each block is its own view spec. Blocks are displayed in order as separate agenda sections.

***** Block Types

Special ~block-type~ values control how blocks are rendered:

- ~calendar-day~ :: Native org-agenda day view filtered to Calendar and Habit items only
- ~todo~ :: Native org-agenda todo block (requires ~todo-keyword~)
- /default/ :: tags block with skip function (when no block-type specified)

***** Native Blocks (Escape Hatch)
:PROPERTIES:
:CUSTOM_ID: native-blocks
:END:

Have you ever wanted your NEXT actions sorted by priority? Or needed a custom skip function for a specialized workflow? The DSL handles most cases, but org-agenda has decades of features. When you hit its limits, ~native~ blocks let you drop down to raw org-agenda syntax---without abandoning the DSL entirely.

****** When You'll Need This

You're building a view and think: "I wish I could sort these by effort" or "I need my custom skip function here." The DSL doesn't support sorting yet. What do you do?

You have two choices:
1. Write the whole view in ~org-agenda-custom-commands~ (losing DSL benefits)
2. Use a ~native~ block for just that section (keeping DSL for the rest)

Option 2 is what this section teaches.

****** Your First Native Block

Start with something you know. This DSL block shows NEXT actions:

#+begin_src emacs-lisp
((type . next-action))
#+end_src

Here's the equivalent as a native block:

#+begin_src emacs-lisp
((native . (tags-todo "LEVEL>0+ORG_GTD=\"Actions\"/NEXT" nil)))
#+end_src

The format is ~(BLOCK-TYPE MATCH-STRING SETTINGS)~---exactly what ~org-agenda-custom-commands~ uses. Try evaluating both in a multi-block view:

#+begin_src emacs-lisp
(org-gtd-view-show
 '((name . "Comparing DSL and Native")
   (blocks . (((name . "DSL Version")
               (type . next-action))
              ((native . (tags-todo "LEVEL>0+ORG_GTD=\"Actions\"/NEXT"
                          ((org-agenda-overriding-header "Native Version")))))))))
#+end_src

They show the same items. The native block is more verbose, but it unlocks org-agenda's full power.

****** Adding Custom Sorting

Now the payoff. Want priority sorting? Add it to the settings list:

#+begin_src emacs-lisp
((native . (tags-todo "+@work/NEXT"
            ((org-agenda-sorting-strategy '(priority-down effort-up))
             (org-agenda-overriding-header "Work by Priority")))))
#+end_src

The settings list can include any org-agenda variable. Common ones:
- ~org-agenda-sorting-strategy~ --- Sort by priority, effort, alphabetically
- ~org-agenda-skip-function~ --- Your custom skip logic
- ~org-agenda-prefix-format~ --- Custom prefix display

****** Mixing DSL and Native

The real power is mixing them. Use DSL for simple blocks, native for complex ones:

#+begin_src emacs-lisp
(org-gtd-view-show
 '((name . "Mixed Dashboard")
   (blocks . (((type . delegated)                               ; DSL: simple
               (when . past))
              ((native . (tags-todo "+urgent"                   ; Native: sorted
                          ((org-agenda-sorting-strategy '(effort-up))
                           (org-agenda-overriding-header "Urgent by Effort")))))
              ((type . next-action))))))                        ; DSL: simple
#+end_src

Each block is independent. Use whatever syntax fits that block's needs.

****** Native Block Types

The BLOCK-TYPE (first element) determines what kind of agenda block you get:

| Block Type   | What It Shows                          |
|--------------+----------------------------------------|
| ~agenda~     | Calendar/timeline (like daily view)    |
| ~todo~       | TODO items by keyword                  |
| ~tags~       | Items matching tag/property expression |
| ~tags-todo~  | Like ~tags~ but only TODO items        |
| ~search~     | Full-text search results               |

****** Quick Reference

*Syntax*:
#+begin_src emacs-lisp
((native . (BLOCK-TYPE MATCH-STRING SETTINGS)))
#+end_src

*Rules*:
- Only valid inside a ~blocks~ list
- Other DSL keys in the same block spec are ignored
- Settings is an alist of ~(org-agenda-variable value)~ pairs

*When to use*: Custom sorting, skip functions, specialized org-agenda settings, or migrating complex views incrementally

*** TODO Keyword Filters

Filter by TODO state.

*Note*: The ~type~ filter automatically includes the correct TODO keyword for each type (e.g., ~next-action~ includes ~NEXT~, ~delegated~ includes ~WAIT~). Use these filters only when you need explicit control.

**** ~(todo . ("KEYWORD1" "KEYWORD2"))~

*Matches*: Items with any of the specified TODO keywords

*Use case*: Show specific states

*Example*: Show only NEXT actions:
#+begin_src emacs-lisp

*Example*: Show NEXT and WAIT:
#+begin_src emacs-lisp
'((name . "Active and Waiting")
  (todo . ("NEXT" "WAIT")))
#+end_src

**** ~(done . VALUE)~

*Matches*: Items with done TODO states (right side of ~|~ in keyword sequence)

*Values*:
- ~t~ :: Any done item, regardless of when closed
- ~NUMBER~ :: Done in last NUMBER days (e.g., ~14~ for last 2 weeks)
- ~today~ :: Done today
- ~recent~ :: Done in last 7 days
- ~past-day~ :: Done in last day
- ~past-week~ :: Done in last week
- ~past-month~ :: Done in last month
- ~past-year~ :: Done in last year

*Use case*: Show completed items, optionally filtered by when they were completed

*Example*: All completed items:
#+begin_src emacs-lisp
'((name . "Completed Items")
  (done . t))
#+end_src

*Example*: Items completed this week:
#+begin_src emacs-lisp
'((name . "Completed This Week")
  (done . past-week))
#+end_src

*Example*: Items completed in the last 14 days:
#+begin_src emacs-lisp
'((name . "Completed in Last 2 Weeks")
  (done . 14))
#+end_src

*Example*: Items completed today:
#+begin_src emacs-lisp
'((name . "Completed Today")
  (done . today))
#+end_src

*** Priority, Effort, and Clocked Filters

Filter by task metadata useful for "quick wins", "deep work", and triage views.

**** ~(priority . VALUE)~

*Matches*: Items with matching priority

*Forms*:
- ~(priority . A)~ :: Single value---matches priority A
- ~(priority . (A B))~ :: List---matches priority A OR B
- ~(priority . (>= B))~ :: Comparison---matches B or higher (A, B)
- ~(priority . nil)~ :: Items with no priority set

*Comparison operators*: ~<~, ~>~, ~<=~, ~>=~

*Note*: A is highest priority (A > B > C). Respects ~org-priority-highest~ and ~org-priority-lowest~ for custom ranges.

*Example*: High priority actions:
#+begin_src emacs-lisp
'((name . "High Priority")
  (type . next-action)
  (priority . A))
#+end_src

*Example*: Important items (A or B):
#+begin_src emacs-lisp
'((name . "Important Tasks")
  (type . next-action)
  (priority . (A B)))
#+end_src

*Example*: All items B or higher:
#+begin_src emacs-lisp
'((name . "Priority B+")
  (type . next-action)
  (priority . (>= B)))
#+end_src

*Example*: Triage items missing priority:
#+begin_src emacs-lisp
'((name . "Needs Priority")
  (type . next-action)
  (priority . nil))
#+end_src

**** ~(effort . SPEC)~

*Matches*: Items with matching Effort property

*Forms*:
- ~(effort . (< "0:30"))~ :: Under 30 minutes
- ~(effort . (> "1:00"))~ :: Over 1 hour
- ~(effort . (between "0:15" "1:00"))~ :: Range (inclusive)
- ~(effort . nil)~ :: Items with no effort estimate

*Duration formats* (all org-mode formats supported):
- ~"3:12"~ :: H:MM
- ~"1:23:45"~ :: H:MM:SS
- ~"1d3h5min"~ :: Units (d, h, min)
- ~"30"~ :: Bare number (minutes)

*Example*: Quick wins (under 15 minutes):
#+begin_src emacs-lisp
'((name . "Quick Wins")
  (type . next-action)
  (effort . (< "15min")))
#+end_src

*Example*: Deep work items (1-2 hours):
#+begin_src emacs-lisp
'((name . "Deep Work")
  (type . next-action)
  (effort . (between "1:00" "2:00")))
#+end_src

*Example*: Triage items missing effort:
#+begin_src emacs-lisp
'((name . "Needs Effort Estimate")
  (type . next-action)
  (effort . nil))
#+end_src

**** ~(clocked . SPEC)~

*Matches*: Items with matching total clocked time

*Forms*:
- ~(clocked . (< "0:30"))~ :: Less than 30 minutes clocked
- ~(clocked . (> "2:00"))~ :: More than 2 hours invested
- ~(clocked . (between "0:30" "2:00"))~ :: Range (inclusive)
- ~(clocked . nil)~ :: Items with no time clocked (0 minutes)

*Use case*: Find items you've already invested time in, or items you haven't started yet.

*Example*: Items with significant time invested:
#+begin_src emacs-lisp
'((name . "Deep in Progress")
  (type . next-action)
  (clocked . (> "1:00")))
#+end_src

*Example*: Not started yet:
#+begin_src emacs-lisp
'((name . "Not Started")
  (type . next-action)
  (clocked . nil))
#+end_src

*Example*: Focus work (high priority, time invested):
#+begin_src emacs-lisp
'((name . "Focus Work")
  (type . next-action)
  (priority . (>= B))
  (clocked . (> "0:30")))
#+end_src

**** ~(last-clocked-out . SPEC)~

*Matches*: Items based on when they were last clocked out

*Forms*:
- ~(last-clocked-out . (> "2d"))~ :: Not worked on in 2+ days
- ~(last-clocked-out . (>= "2d"))~ :: Not worked on in 2+ days (inclusive)
- ~(last-clocked-out . (< "1w"))~ :: Worked on within past week
- ~(last-clocked-out . (<= "1w"))~ :: Worked on in past week (inclusive)
- ~(last-clocked-out . nil)~ :: Never clocked

*Duration formats*:
- ~"2d"~ :: 2 days
- ~"1w"~ :: 1 week
- ~"3h"~ :: 3 hours
- ~"30m"~ :: 30 minutes

*Project handling*: For project headings, automatically checks all tasks
in the project and uses the most recent clock-out time.

*Example*: Find stale projects not worked on in a week:
#+begin_src emacs-lisp
'((name . "Stale Projects")
  (type . project)
  (last-clocked-out . (> "1w")))
#+end_src

*Example*: Find items never started:
#+begin_src emacs-lisp
'((name . "Never Started")
  (type . next-action)
  (last-clocked-out . nil))
#+end_src

**** Prefix DSL: Customizing the Task Prefix Column
:PROPERTIES:
:CUSTOM_ID: prefix-dsl
:END:

When you look at your engage view, you see context information on the left of each task---like the project name. The Prefix DSL lets you control what appears there using a simple fallback chain.

*Mental model:* Think of the prefix like a label maker. You specify what you /want/ to show, in order of preference. org-gtd tries each option until one has a value.

***** Your First Prefix in 60 Seconds

Try this now (evaluate with ~M-x eval-region~):

#+begin_src emacs-lisp
(org-gtd-view-show
 '((name . "Tasks with Context")
   (prefix . (project area-of-focus "—"))
   (type . next-action)))
#+end_src

You'll see NEXT actions with:
- The project name (if the task is in a project)
- Or the area of focus (if no project, but area is set)
- Or a dash "—" (if neither is available)

That's the fallback chain in action.

***** ~(prefix . (ELEMENT ...))~

*Purpose*: Control what context appears before each task in the view

*Format*: A list of elements, tried in order. First non-empty value wins.

*Available elements*:
- ~project~ :: The project heading this task belongs to
- ~area-of-focus~ :: The ~CATEGORY~ property (your GTD area of focus)
- ~file-name~ :: The base name of the file containing the task
- ~"literal string"~ :: Any quoted string (used as fallback)

*Example*: Show project, fallback to area, then to literal text:
#+begin_src emacs-lisp
'((name . "My View")
  (prefix . (project area-of-focus "No Context"))
  (type . next-action))
#+end_src

*Example*: Just show the project name (or nothing):
#+begin_src emacs-lisp
'((name . "Project Tasks")
  (prefix . (project))
  (type . next-action))
#+end_src

*Example*: Tickler items labeled "Incubated":
#+begin_src emacs-lisp
'((name . "Tickler Items")
  (prefix . ("Incubated"))
  (type . tickler))
#+end_src

***** ~(prefix-width . N)~

*Purpose*: Control how many characters the prefix column uses

*Default*: Uses ~org-gtd-prefix-width~ (default: 12)

*Note*: Long values are truncated with ~org-gtd-agenda-truncate-ellipsis~ (default "…"). Short values are padded with spaces.

*Example*: Extra space for long project names:
#+begin_src emacs-lisp
'((name . "Wide Prefix View")
  (prefix . (project area-of-focus))
  (prefix-width . 20)
  (type . next-action))
#+end_src

***** Prefix Inheritance in Multi-Block Views

When you define ~prefix~ at the view level, all blocks inherit it:

#+begin_src emacs-lisp
'((name . "My Dashboard")
  (prefix . (project area-of-focus "—"))  ;; All blocks use this
  (prefix-width . 15)
  (blocks . (((name . "Calendar Today")
              (type . calendar)
              (when . today))
             ((name . "NEXT Actions")
              (type . next-action)))))
#+end_src

Individual blocks can override the inherited prefix:

#+begin_src emacs-lisp
'((name . "Mixed Prefixes")
  (prefix . (project))  ;; Default for blocks
  (blocks . (((name . "Projects")
              (prefix . ("Project"))  ;; Override: literal label
              (type . active-project))
             ((name . "NEXT Actions")
              ;; Uses inherited (project) prefix
              (type . next-action)))))
#+end_src

***** Low-Level: ~(prefix-format . FORMAT-STRING)~

For advanced users who need full control, you can specify the raw org-agenda prefix format string. This bypasses the prefix DSL.

*Example*:
#+begin_src emacs-lisp
'((name . "Custom Format")
  (prefix-format . " %i %-12:(org-gtd-agenda--resolve-prefix-chain '(project) 12) ")
  (blocks . (((name . "NEXT Actions")
              (type . next-action)))))
#+end_src

Most users should use ~(prefix . ...)~ instead.

**** ~(view-type . agenda)~

*Purpose*: Create a day/week org-agenda view instead of a tags block

*Use case*: When you want a standard day/week agenda view

*Example*:
#+begin_src emacs-lisp
'((name . "Weekly Agenda")
  (view-type . agenda)
  (agenda-span . 7))
#+end_src

**** ~(agenda-span . N)~

*Purpose*: Number of days to show in agenda view

*Default*: 1

*Requires*: ~(view-type . agenda)~

*** Simplified Multi-Block Views
:PROPERTIES:
:CUSTOM_ID: simplified-view-specs
:END:

Creating multi-block views usually requires verbose ~blocks~ syntax. The View DSL offers a simpler alternative: just list the types you want to see.

*For:* Users who want quick multi-block views without boilerplate.

**** The Problem: Verbose Block Definitions

A typical area-of-focus review view requires this:

#+begin_src emacs-lisp
;; Verbose: every block needs explicit configuration
'((name . "Health Review")
  (blocks . (((name . "Projects")
              (type . project)
              (area-of-focus . "Health"))
             ((name . "Next Actions")
              (type . next-action)
              (area-of-focus . "Health"))
             ((name . "Calendar")
              (type . calendar)
              (area-of-focus . "Health")
              (when . today)))))
#+end_src

Notice the repetition: ~area-of-focus~ appears in every block, and you had to remember that ~calendar~ needs ~(when . today)~.

**** The Solution: Implicit Blocks

The same view, simplified:

#+begin_src emacs-lisp
;; Concise: types expand automatically with smart defaults
'((name . "Health Review")
  (area-of-focus . "Health")
  (type . project)
  (type . next-action)
  (type . calendar))
#+end_src

When you list multiple ~type~ keys at the top level, org-gtd automatically:
1. Creates a block for each type
2. Inherits top-level filters (~area-of-focus~) to all blocks
3. Applies smart defaults (e.g., ~calendar~ gets ~(when . today)~)

**** Try It Now

Evaluate this (select and run ~M-x eval-region~):

#+begin_src emacs-lisp
(org-gtd-view-show
 '((name . "Quick Dashboard")
   (type . next-action)
   (type . delegated)
   (type . tickler)))
#+end_src

You get three sections:
- "Next Actions" - all your NEXT tasks
- "Delegated" - items due today (smart default: ~when . today~)
- "Tickler" - reminders due today (smart default: ~when . today~)

No ~blocks~ syntax. No ~when~ filters. org-gtd inferred them.

**** Smart Type Defaults

Time-sensitive types automatically filter to "today":

| Type | Default ~when~ | Default Name |
|------+----------------+--------------|
| ~calendar~ | ~today~ | "Calendar" |
| ~delegated~ | ~today~ | "Delegated" |
| ~tickler~ | ~today~ | "Tickler" |
| ~habit~ | --- | "Habits" |
| ~next-action~ | --- | "Next Actions" |
| ~project~ | --- | "Projects" |
| ~someday~ | --- | "Someday/Maybe" |
| ~stuck-project~ | --- | "Projects (Needs Attention)" |

*Why these defaults?* For calendar, delegated, and tickler items, you usually want to see what's relevant /today/. For other types, you want to see everything.

**** Top-Level Inheritance

Filters at the top level apply to /all/ blocks:

#+begin_src emacs-lisp
'((name . "Work Focus")
  (area-of-focus . "Work")  ;; Applied to all blocks
  (type . project)
  (type . next-action)
  (type . delegated))
#+end_src

This shows only Work-related items across all three sections.

**** The Four-Tier Precedence Model

When org-gtd expands implicit blocks, it applies settings in this order (highest priority first):

1. *Block-explicit* --- If you use explicit ~blocks~ syntax and set a value, it wins
2. *Top-level* --- Filters at the view's top level inherit to all blocks
3. *Type smart default* --- Built-in defaults for that type (e.g., ~calendar~ → ~when . today~)
4. *Global defaults* --- Package defaults like ~org-gtd-prefix-width~

*Example*: Override a smart default:

#+begin_src emacs-lisp
;; Show ALL calendar items, not just today
'((name . "All Calendar")
  (when . future)  ;; Top-level overrides type default
  (type . calendar))
#+end_src

*Example*: Mix explicit and implicit:

#+begin_src emacs-lisp
'((name . "Mixed View")
  (area-of-focus . "Work")
  (type . next-action)  ;; Gets "Next Actions" name, Work filter
  (type . delegated))   ;; Gets "Delegated" name, Work filter, when=today
#+end_src

**** When to Use Explicit Blocks

Use explicit ~blocks~ syntax when you need:
- Custom block names (implicit blocks use default names)
- Different filters per block (beyond inheritance)
- Non-standard block types like ~calendar-day~ or ~todo~

*Example*: Custom names require explicit blocks:

#+begin_src emacs-lisp
'((name . "My Dashboard")
  (blocks . (((name . "Today's Schedule")  ;; Custom name
              (block-type . calendar-day))
             ((name . "Ready to Work On")  ;; Custom name
              (type . next-action)))))
#+end_src

**** Quick Reference

| Goal | Use |
|------+-----|
| Simple multi-section view | Multiple ~(type . X)~ keys |
| Custom block names | Explicit ~blocks~ |
| Filter all blocks | Top-level filter |
| Override smart default | Top-level filter |
| Mix native + query blocks | Explicit ~blocks~ |

*** Saving Your Custom Views

Once you have a view you like, save it as a command:

1. *Wrap in a function*:
   #+begin_src emacs-lisp
   (defun my-custom-view ()
     "Description of what this view shows."
     (interactive)
     (org-gtd-view-show
      '((name . "View Name")

2. *Bind to a key* (optional):
   #+begin_src emacs-lisp

*** What Are Organize Hooks?

Hooks let you automatically capture information about tasks as you organize them—like tracking when tasks were created, auto-tagging items with "urgent" in the title, or estimating effort based on keywords.

Without hooks, you'd manually add the same metadata to every task. With hooks, you define the pattern once and org-gtd applies it automatically during organization.

For anyone who wants consistent metadata on their GTD items without repetitive manual work.

*** Your First Hook in 2 Minutes

Let's add automatic creation timestamps to all tasks except trash and quick actions.

1. Add this to your config:
   #+begin_src emacs-lisp
   (defun my-track-creation-date ()
     "Add CREATED property with current timestamp."
     (unless (org-gtd-organize-type-member-p '(trash quick-action))
       (org-set-property "CREATED"
                         (format-time-string "[%Y-%m-%d %a %H:%M]"))))

   (add-to-list 'org-gtd-organize-hooks 'my-track-creation-date)
   #+end_src

2. Restart Emacs (or eval the code with ~C-x C-e~)

3. Capture something: ~M-x org-gtd-capture~, type "Test task", finish capture

4. Process it: ~M-x org-gtd-process-inbox~, organize as "Single action"

5. Look at the task: you'll see a CREATED property with today's timestamp

You just automated metadata capture. Every item you organize now gets timestamped automatically.

*** The org-gtd-organize-hooks Variable

*Type*: List of functions

*When run*: During ~org-gtd-organize~, after you choose item type but before refiling

*Purpose*: Add metadata (tags, properties, etc.) to items as they're organized

*Default value*: ~'(org-set-tags-command)~

*** Built-in Hooks

**** ~org-set-tags-command~

*What it does*: Prompts for tags to add to the item

*Use when*: You want to tag items during organization (default)

*To use*:
#+begin_src emacs-lisp
(setq org-gtd-organize-hooks '(org-set-tags-command))
#+end_src

**** ~org-gtd-set-area-of-focus~

*What it does*: Prompts for area of focus (from ~org-gtd-areas-of-focus~) and sets CATEGORY property

*Use when*: You use GTD Horizon 2 (areas of focus)

*To use*:
#+begin_src emacs-lisp
(setq org-gtd-organize-hooks '(org-set-tags-command
                               org-gtd-set-area-of-focus))
#+end_src

*Behavior*: Skips prompt for:
- Project tasks (sets on project instead)
- Trash items
- Knowledge items
- Quick actions

*** Writing Custom Hooks

Custom hooks are functions that run during organization. They can:
- Add properties
- Set tags
- Modify heading text
- Prompt for information
- Skip certain item types

**** Basic Hook Structure

#+begin_src emacs-lisp
(defun my-organize-hook ()
  "Description of what this hook does."
  (interactive)  ;; hooks can be interactive or not
  ;; Your code here
  ;; Point will be on the heading being organized
  ;; Use org-mode functions to modify it
  )
#+end_src

**** Using org-gtd-organize-type-member-p

This helper function lets you run code only for specific item types.

*Function signature*:
#+begin_src emacs-lisp
(org-gtd-organize-type-member-p TYPE-LIST)
#+end_src

*Arguments*:
- ~TYPE-LIST~ :: List of item type symbols to check against

*Returns*: ~t~ if current item matches one of the types, ~nil~ otherwise

*Available types*:
- ~'single-action~ :: Single actions (do when possible)
- ~'project-heading~ :: Project headings (top-level project info)
- ~'project-task~ :: Tasks within projects
- ~'calendar~ :: Calendar items (do at a given time)
- ~'delegated~ :: Delegated items (done by someone else)
- ~'tickler~ :: Tickler items (remind me later - has a specific date)
- ~'someday~ :: Someday/maybe items (no specific timeframe)
- ~'habit~ :: Habits (recurring actions)
- ~'knowledge~ :: Reference items (stored as reference)
- ~'quick-action~ :: Quick actions (<2 min)
- ~'trash~ :: Trashed items
- ~'everything~ :: Special value: if in the list, always return t

*Example*: Only run for single actions and project headings:
#+begin_src emacs-lisp
(defun my-hook ()
  (when (org-gtd-organize-type-member-p '(single-action project-heading))
    ;; do something
    ))
#+end_src

*** Example Custom Hooks

**** Selective Tagging with Unless

The most common pattern is "run this hook for everything EXCEPT certain types". This example prompts for tags on all items except trash and knowledge (reference):

#+begin_src emacs-lisp
(defun my-tag-tasks ()
  "Prompt for tags on all items except trash and knowledge."
  (unless (org-gtd-organize-type-member-p '(trash knowledge))
    (org-set-tags-command)))

(setq org-gtd-organize-hooks '(my-tag-tasks))
#+end_src

This replaces the default ~org-set-tags-command~ with selective tagging. The ~unless~ pattern is cleaner than listing all the types you DO want: it says "skip these few, run for everything else."

**** Set Effort from Keywords

#+begin_src emacs-lisp
(defun my-auto-set-effort ()
  "Automatically set effort based on keywords in heading."
  (when (org-gtd-organize-type-member-p '(single-action))
    (let ((heading (downcase (org-get-heading t t t t))))
      (cond
       ((string-match-p "quick\\|call\\|email" heading)
        (org-set-property "Effort" "0:15"))
       ((string-match-p "meeting\\|review" heading)
        (org-set-property "Effort" "1:00"))
       ((string-match-p "research\\|write\\|design" heading)
        (org-set-property "Effort" "2:00"))))))

(add-to-list 'org-gtd-organize-hooks 'my-auto-set-effort)
#+end_src

*** Hook Execution Order

Hooks run in the order they appear in ~org-gtd-organize-hooks~.

*Example*: Set area first, then tags:
#+begin_src emacs-lisp
(setq org-gtd-organize-hooks
      '(org-gtd-set-area-of-focus  ;; runs first
        org-set-tags-command))      ;; runs second
#+end_src

This order matters if one hook depends on another's results.

*** Best Practices

1. *Use type checking*: Always use ~org-gtd-organize-type-member-p~ to run hooks only for relevant item types

2. *Keep hooks focused*: Each hook should do one thing well

3. *Make hooks optional*: Use ~y-or-n-p~ for optional metadata:
   #+begin_src emacs-lisp
   (when (y-or-n-p "Add custom property? ")
     (org-set-property "PROP" value))
   #+end_src

4. *Test interactively*: Make hooks interactive for testing:
   #+begin_src emacs-lisp
   (defun my-hook ()
     (interactive)  ;; can test with M-x my-hook
     ...)
   #+end_src

5. *Handle errors gracefully*: Wrap risky code in condition-case:
   #+begin_src emacs-lisp
   (condition-case err
       (my-risky-operation)
     (error (message "Hook failed: %s" err)))
   #+end_src

6. *Document your hooks*: Add docstrings explaining what each hook does
