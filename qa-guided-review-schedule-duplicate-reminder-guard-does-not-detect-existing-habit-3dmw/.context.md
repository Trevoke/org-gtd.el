SYMPTOM (PR #294 QA, user-confirmed): running M-x org-gtd-review-schedule a second time
creates a duplicate review-reminder habit; the "A review reminder already exists —
schedule another?" y-or-n-p never fires, so org-gtd-review--reminder-exists-p returns
nil even though a habit exists.

MECHANISM (from code): org-gtd-review--reminder-exists-p and --insert-reminder-body scan
(org-gtd--default-file) = org-gtd-tasks.org and look for a heading whose title equals a
profile name AND ORG_GTD == habit marker. But the habit is created by
org-gtd-review-schedule via org-gtd-create-item (quote habit) -> org-gtd-process-heading,
which REFILES the item to the habit type target. Prime suspects for the miss:
  (a) refile target file != org-gtd--default-file (guard scans wrong buffer), and/or
  (b) the refiled habit heading title is not exactly the profile name (org-get-heading
      t t t t mismatch), and/or ORG_GTD value differs from (org-gtd-type-org-gtd-value
      (quote habit)).
VERIFY during fix: print (buffer-file-name (org-gtd--default-file)) vs the file the habit
lands in, and the created heading title + ORG_GTD prop.

habit creation path prompts interactively (area-of-focus / scheduling) despite :when
config. So the regression test must stub the interactive bits (cl-letf) or assert on
